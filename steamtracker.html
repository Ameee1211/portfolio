01 — The short version

A number Steam won't give you: how much you played today.

Steam counts hours for a lifetime. Nobody counts them for an evening. That gap is the whole project — one page, one form, and a list that keeps the sessions you bothered to write down.

The problem
Lifetime totals don't change behaviour. A number in the hundreds is easy to ignore. The two hours you played tonight is not, and no Steam screen shows it.
The build
Three fields and a card. Type the game, the hours and the genre, check the card, add it to today. Nothing is saved until you have seen it written out.
The limit
It only knows what you type. No Steam login, no automatic import, no cover art. The trade was deliberate, and section 03 is about why.

02 — Why this exists

The brief was media consumption. I picked the number that gets noticed.

The assignment was a web application about media consumption. I chose games because the tracking already exists there — Steam has counted every hour since before I had an account. What it does with that data is the problem: it adds all of it up, forever, and shows you a figure so large that it stops meaning anything.

So the app is built around one number, the total for a day. It sits beside the date on every entry, it is the only arithmetic the app performs, and it is the reason to open it again tomorrow.

03 — Choosing a direction

The first design needed an API that turned out not to exist.

My first mockup pulled names and box art straight from Steam: type a title, see the real cover, add it. Then I went looking for the endpoint. Everything Steam publishes is library-scoped — it needs a user's Steam ID and their permission to read their own games. An index of the whole store, with pictures, is not public.

Designed first

Auto-fill from Steam

The user types a title; the app fetches the correct name, the cover art and the genre, then fills the card for them. It looked finished in a mockup.

Dropped because: there is no public endpoint to call. Keeping it would have meant hard-coding fake games — a demo that works only on the data I invented.

Shipped
Rebuilt around

Three fields, typed by hand

Name, hours, genre. No pictures, no fetching, and no game the app can't record — including the ones no store listing would return.

Kept because: it works for every game and for nobody's data but the user's. It also made the daily total the only thing left to look at.

04 — The logic under the interface

Nothing reaches the history until it has been checked, and nothing gets checked until it is complete.

The form has two steps and a gate between them. Check reads the three fields, and if anything is wrong it says so under the field that is wrong. Only a complete, well-formed entry produces a card, and only a card can be added to the history.

Everything empty

“Please enter the game information.”

Two decimal places

“Please enter a numeric value with one decimal place.”

Add before Check

“Cannot be added to game history. Please finish step 1 first.”

Missing name“Please enter the Game Name.”
Missing playtime“Please enter the Playtime.”
No genre“Please select the Category.”
Words, or two decimalsOne pattern rejects both: digits, with at most one place after the point.

Six messages in total, each written in the place the mistake was made. Nothing opens a dialog, and nothing scrolls you somewhere else to tell you off.

05 — Three fields, once a session

The whole app, in four screens.

There is no menu and there are no settings. The loop is the same every time, and the history only grows when you confirm a card you have already read.

Step 01

Fill in three fields

Name, hours to one decimal place, and one of eleven genres. Clear empties all three at once, which was the tutor's suggestion.

Step 02

Read it back on the card

Check writes the entry into a mint card: name, genre, this session, the running total for that game, and the date. Nothing is saved yet.

Step 03

Add it to the list

Add puts the entry at the top of the history and resets the card to NA, ready for the next one. The total above the list goes up straight away.

Step 04

Open a row, or delete it

The arrow opens the entry to show its genre and its total across every session of that game. Delete only appears once a row is open, so removing takes two clicks.

06 — It is a website, so use it

The build runs below. The repository link does not.

This is the real application, not a recording of one. Add a game, watch the total change, refresh the page and it is still there. Your entries live in your own browser and I cannot see them.

Try “Hollow Knight”, 2.0, Action — then Check, then Add. Open in a new tab ↗

Why the GitHub link never opened on another computer. Nothing in the code is broken. The repository was simply never publishable, for three reasons that stack up in the order you would meet them.

01
There is no index.html at the root
The site lives in /public. GitHub Pages serves the repository root, so github.io/<repo> answers with a 404. There is nothing there for it to open.
02
The built folder is ignored by git
server.js serves /dist, and dist sits in .gitignore. Even with Node installed there is no compiled site to serve until parcel build has run.
03
The README's first instruction needs a step before it
npm run dev needs node_modules, and a fresh clone has none. The lockfile pins Parcel 2.9 and Sass from 2023, so npm install has to succeed before anything runs at all.

The fix was to stop asking people to build it. Once Parcel has done its pass the app is a folder of static files, so I copied that folder into this site. Same code, no install, works on any machine with a browser.

07 — What happens underneath

An array in localStorage, and one function that redraws all of it.

There is no database and no server-side state. The entire app is one array stored in the browser, and everything on screen — the cards, the dates, the totals, their order — is rebuilt from that array when the page loads and again after every change.

What one record holds

  • name — the game, as typed
  • playtime — this session, one decimal place
  • category — one of the eleven genres
  • totalPlaytime — every session of that game so far
  • date — the day it was added

Nothing else. No Steam ID, no account, no timestamp beyond the day.

The part that was hard

updateGameHis() — lines 171 to 253 of the 291-line script.js — empties the list, reads the array back out of localStorage, writes a card for each record, then attaches the open and delete handlers to elements that did not exist a moment ago. It is the longest function in the file and the only one I commented line by line, because when it goes wrong the list either doubles or disappears.

Read on loadThe list is rebuilt from localStorage every time the page opens.
Write on changeAdd and Delete rewrite the same array, then call the same redraw.
Newest firstRecords are pushed to the front, so the last session sits at the top.
Totals are not per dayThe number above each card adds up the whole array, which only equals one day while the list is one day long.

That last point is a real gap between the mockup and the build. The redrawn mockup groups every game under a single date header; the finished code gives each record its own header and repeats the running total on it. It reads fine for two sessions and would need fixing at fifty.

08 — Mockup to mockup

The first version was bright, full width, and had no way to clear the form.

My tutor's feedback on version one was blunt: you cannot read the game information against that background. So I went and looked at sites that are easy to read, and wrote down what they had in common — a white page with a single accent colour, content held inside margins instead of stretched across a wide screen, and instructions placed where the user is about to act.

Mint greenChosen as the single accent because it sits next to Steam without copying it.
MarginsContent pulled into the middle so a wide screen still reads left to right.
ClearOne button to empty all three fields — the tutor's suggestion.
DividersFour sections made visible, so the page reads in steps rather than as one column.

There is no version two for mobile, and that was a decision rather than an omission: the phone layout only has to move the second step underneath the first, so drawing it again would have told me nothing the grid had not already told me.

09 — Phone, tablet, desktop

Three blocks in the SCSS, but only one breakpoint that changes the layout.

Above 1024px the two steps sit side by side: you type on the left and read the result on the right without moving your eyes. At 1024px and below that stops being possible, so the grid collapses and the preview card drops underneath the form, in the order you use it.

10 — How it was built

Week six was the server. Week eight was the bundler.

The build followed the course in order. First a Node and Express server serving a static folder, then Parcel and SCSS on top of it, then the form and the history. Nine commits between 28 May and 7 June 2023, one working step in each.

01

Nine commits, named for the change

From “add the homepage” to “finish mobile version”. Small enough that any one of them could be the version that worked.

02

SCSS for the repetitive part

Nested selectors and a loop saved the responsive layer from being written out three times by hand. It is also the least tidy code in the project.

03

A background that explains the app

The homepage is one image from Steam's own store art, so the subject is obvious before a word is read. It still scrolls instead of staying put.

04

localStorage, the slow part

Reading, ordering, summing and redrawing the list on every change is the only piece of the build that genuinely slowed me down.

11 — Known issues & future versions

What it cannot do yet, and the one thing it now can.

These are the four I wrote down when the assignment was handed in, in the order I would tackle them. Only the last one is finished, and it was finished here rather than in the repository.

01

The responsive SCSS is longer than it needs to be

The tablet and phone blocks repeat rules that differ only by a margin. They work, and they are the least tidy code in the project.

Next version: fold both into one mixin that takes the spacing as an argument, instead of writing the block out twice.

02

No Steam integration

Every session is typed by hand, so the app can only report what you remembered to record — the one thing a tracker should not depend on.

Next version: let the user connect their own library with their permission and fill the history from it. That is the version I drew first, before I found out the API was library-scoped.

03

The homepage background scrolls away

The Steam artwork moves with the page instead of staying put, so the one moment that sets the mood is gone as soon as you move.

Next version: background-attachment: fixed on desktop and a static crop on mobile, where the fixed version behaves badly.

04

It only opened on the machine that had the files

The app needed Node, a Parcel build and a local server, so the repository was not a link to anything a tutor or a friend could actually use.

Done here: the compiled folder is static, so the app now runs in section 06 of this page and in a new tab, on any machine with a browser. No install, no build.
